# Deploy the T3 integration

These examples run one central T3 web service, one agent-runtime control service,
and retained execution workspaces. They require an existing Kubernetes cluster
with the Agent Sandbox `agents.x-k8s.io/v1beta1` controller and an existing
Hatchet installation. The examples are not applied automatically.

## Prepare the images and storage

1. Build and verify the three targets using the [image build guide](../../images/t3/README.md).
2. Publish the verified artifacts to your registry and replace each
   `REPLACE_REGISTRY/...@sha256:REPLACE_DIGEST` value with its immutable image
   reference.
3. Replace `REPLACE_STORAGE_CLASS` in `web.yaml` and `t3-profiles.json`.

Use a storage class that supports SQLite filesystem semantics for central state.
Keep the central deployment at one replica with the `Recreate` update strategy.
The `/data` volume holds the full T3 state directory, including SQLite, settings,
secrets, attachments, and artifacts. Back up that directory through a consistent
SQLite backup procedure.

Execution workers mount a separate retained PVC at `/workspace`. Agent-runtime
owns these PVCs and the direct Sandbox allocations. Suspending or releasing
compute retains the workspace PVC. Do not add a `workspace` volume definition to
the profile; the controller supplies it. The worker's home and journal are
inside that retained volume. Conversation SQLite stays on the central volume.

Suspension shuts down worker processes; it does not freeze their memory. Idle
conversations suspend after `T3_SANDBOX_IDLE_MS`, which defaults to five minutes.
Pending provider approvals or input callbacks, active delegated work, and running
subprocesses keep the workspace alive until they can stop safely. Settling a
conversation releases compute after its cleanup finishes. Both paths retain the
workspace PVC so later activity can start a new worker against the same files.

## Supply credentials

Create these Kubernetes Secrets through your existing secret-management process.
No example contains a credential value.

| Namespace | Secret | Required keys |
| --- | --- | --- |
| `t3-control` | `t3-runtime-secrets` | `runtime-key`, `t3-control-token`, `hatchet-client-token` |
| `t3-workspaces` | `t3-git-credentials` | `credentials.json` |
| `t3-workspaces` | `t3-execution-environment` | The approved provider and source-control environment for this execution profile |

Use at least 32 random bytes for `runtime-key` and a separate bearer token of at
least 32 characters for `t3-control-token`. The central `AGENT_RUNTIME_TOKEN` and
runtime control-token file reference the same key. Keep `runtime-key` stable
across restarts because it protects lifecycle state and workspace credentials.

The Hatchet client token contains its connection configuration. If your Hatchet
installation requires endpoint or TLS overrides, add the matching Hatchet SDK
environment variables to `runtime.yaml`. Do not disable TLS for a remote Hatchet
endpoint.

The execution-environment Secret is loaded into every worker using this profile,
including utility workers. Give separate profiles separate Secrets when their
credential access differs. Keep profile credentials limited to the repositories
and provider accounts that the profile may use. The example projects `t3-git-credentials` read-only and sets
`T3_GIT_CREDENTIALS_FILE`. Its `credentials.json` has this shape:

```json
{
  "credentials": [
    {"protocol": "https", "host": "git.example.com", "username": "git-user", "token": "REPLACE_TOKEN"}
  ]
}
```

The image helper accepts only HTTPS and matches the complete host, including any
port. Unknown hosts receive no credential. The helper never stores or erases
Secret contents, and returns a matching token only on Git's credential stdout.
Use an empty `credentials` array for a profile without private HTTPS repositories.
The entrypoint configures the helper in the worker's global Git configuration;
that file contains the helper path, not tokens.

For GitHub environment authentication instead, remove the projected credential
file environment variable and mount. The entrypoint configures `gh auth
git-credential` for `github.com` when `GH_TOKEN` or `GITHUB_TOKEN` is set. Enterprise
tokens require `GH_HOST` and configure that exact HTTPS authority. SSH profiles
need an explicit SSH configuration, keys, and known-hosts mount.

Central source-control API tokens and native Git transport credentials are
separate. Adding an API token through the central UI does not configure workers'
Git transport.
Do not copy a developer's entire home directory into the image or a workspace.

Worker authentication tokens and allocation identities are generated by
agent-runtime. Do not override `T3_WORKER_TOKEN`, `T3_WORKSPACE_ID`,
`T3_ALLOCATION_ID`, `T3_ALLOCATION_GENERATION`, or `T3_POD_UID` in the profile or
its environment Secret.

## Connect the services

Keep the runtime service and execution ports private to the cluster. Central T3
must reach runtime port 8084 and the worker allocation endpoints on port 8083.
The runtime must also reach the workers. Workers need DNS, Git/provider network
access, and the central MCP endpoint.

`T3_MCP_ADVERTISED_URL` is the complete MCP URL reachable from workers, including
`/mcp`. The example uses the internal central Service URL. If a reverse proxy
changes the path, replace it with that proxy's reachable MCP URL.

Expose the central web Service through your existing HTTPS ingress or reverse
proxy. Preserve WebSocket connections and the application's authentication flow.
Do not expose the runtime API or worker bearer tokens to browser clients.

## Open the sandbox IDE

The existing T3 **Open in VS Code** action opens the current thread's sandbox IDE
in a new browser tab. Set `T3CODE_SANDBOX_IDE_ORIGIN` in `web.yaml` to a dedicated
base origin, for example `https://ide.example.com`. Configure wildcard DNS and
TLS for `*.ide.example.com` and route those hosts to the central `t3-web` Service,
preserving WebSocket upgrades. The application assigns each IDE session its own
subdomain. Do not use the main T3 application origin for sandbox content.

T3 exchanges a short-lived bootstrap ticket for an IDE-only session cookie and
proxies HTTP and WebSocket requests through the authenticated execution worker.
The worker selects its loopback code-server service on port 8085. Browser clients
never receive a worker bearer token or Kubernetes pod address. Sessions are tied
to the workspace allocation and become invalid after worker replacement.

The worker entrypoint runs `agent-runtime t3-session`, which starts the desktop,
browser, AIO tools, and code-server before accepting execution traffic on port
8083. VS Code user data and extensions live under
`/workspace/.t3-worker/ide` on the retained volume. T3 terminals and IDE terminals
use the retained worker home and inherit the same display, X authority, and
session bus. T3's interactive preview attaches to the visible Chromium, and its
computer-use MCP tools operate on the full desktop through AIO.

The sample profile explicitly sets `SANDBOX_CHROMIUM_SANDBOX=disabled` because
the restricted container cannot create Chromium's nested sandbox namespaces.
The Kubernetes sandbox remains the execution isolation boundary. Deployments
that allow Chromium's own sandbox can set this to `enabled`. The generic sandbox
image continues to enable it by default. A startup probe gives desktop services
time to start before the worker is considered ready.

The example runs all containers as UID/GID 1000, drops Linux capabilities, and
disables automatic Kubernetes API credentials in web and execution pods. The
runtime ServiceAccount receives only the workspace namespace permissions needed
for retained PVCs, Sandboxes, allocation Secrets, and Pod observation. Add a
sandboxed runtime class and network policy appropriate to your cluster before
running untrusted repositories.

## Render and review

```sh
kubectl kustomize deploy/t3 > /tmp/t3-rendered.yaml
```

Review the rendered images, storage classes, Secret references, RBAC, and network
routes before applying it through your normal deployment process. The ConfigMap
name changes when the profile changes. Existing allocations retain their
recorded profile identity; do not assume a profile edit mutates active workers.

After deployment, check `/healthz` on the runtime Service, then open the central
web application through its authenticated public origin. Import a repository,
start a thread, and verify a provider turn and a Git operation. Stop and resume
that workspace separately to confirm retained storage and replacement behavior
on the actual cluster.

The local validation command in the build guide checks configuration shape.
Image smoke tests check package boot and loopback HTTP. Neither check verifies
Hatchet connectivity, storage provisioning, provider authentication, or lifecycle
replacement in your cluster.
