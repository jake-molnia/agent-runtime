## Decision

Choose candidate B's semantic worker execution boundary as the coherent base. Graft candidate A's provider/MCP audit and conservative spike restart contract onto it. Use the lifecycle report's direct Sandbox plus externally retained PVC and existing agent-runtime/Hatchet workflow approach. All three reports actually recommend worker-local adapters; their substantive disagreement is the recovery promise, not whether adapters should move. The synthesized report may require proven central reattachment before production to preserve existing behavior; conservative interruption is an explicitly limited spike, not a substitute for that release gate.

There is one central T3 server, one stable environment identity, and one SQLite writer with its whole data directory on its PVC. A separate persistent workspace belongs to each ordinary top-level thread. App-owned delegated descendants recursively inherit that workspace; provider sessions, runs, MCP authorization, and conversation identities remain distinct. The sandbox contains a private TypeScript execution worker and the pinned provider executables, plus the generic agent-runtime facilities needed to reach them. It contains no T3 UI, pairing flow, conversation projection database, independent project catalog, or allocator. Hatchet and Go agent-runtime execute lifecycle transitions; Kubernetes resources and authenticated worker observations establish actual readiness.

Candidate B best covers the filesystem/process consumers that would otherwise remain incorrectly central. Candidate A supplies the harder SDK and token questions B does not settle. The lifecycle report prevents a plausible-looking design from deleting native history on claim release. The proposal still needs implementation proofs. In particular, candidate B's central-restart reattachment is a target capability, not an existing behavior.

## Scores and rejected approaches

Scores are design suitability on a five-point scale. They do not rate implemented readiness.

| Criterion | Central adapters with remote process/files | Worker adapters and local semantic execution |
| --- | ---: | ---: |
| Fits central SQLite and runtime/Hatchet authority | 4 | 5 |
| Supports all built-in SDK/process ownership | 1 | 5 |
| Covers workspace, Git, terminal, preview, assets | 2 | 4 |
| Has a credible recovery contract | 3 | 3 |
| Minimizes continuing provider fork drift | 2 | 4 |
| Supports retained workspace and root/child isolation | 5 | 5 |
| Total | 17/30 | 26/30 |

Remote process/files can support a bounded Codex/ACP spike. It loses as the complete built-in architecture because injected Effect services cannot intercept SDK-owned spawning and direct Node/native filesystem calls. Claude calls SDK `query`; Cursor owns SDK sessions; Muse calls SDK `spawnMspConnection`. These are concrete escape paths, not speculative future incompatibilities. See A:38-46 and `T3/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:605`, `Adapters/CursorAdapterV2.ts:2198`, `T3/apps/server/src/provider/museSdk.ts:85`. Native PTY, search index and browser launch independently escape this boundary. See B:76-92 and `T3/apps/server/src/terminal/NodePtyAdapter.ts:274`, `workspace/WorkspaceSearchIndex.ts:303`, `preview/ServerBrowserContexts.ts:64`.

Remote services would still need local compound operations for Git, terminal process inspection, browser profiles and descriptors. That converges on the recommended worker while adding exceptions inside each adapter. Preserve the existing adapter drivers locally and put the serializable seam at session operations and events. A remote Effect filesystem remains useful inside narrowly suitable implementations; it is not a transparent remote operating system.

Exclude full T3 servers per sandbox, central SQLite mounts in workers, a new lifecycle database, a general remote OS emulator, and one service per feature. Also exclude mandatory warm allocation, uninterrupted callback recovery after worker death, a new distributed checkpoint transaction, and native desktop preview parity from the first-release promise. Those do not solve the fixed constraints at minimal scope.

## Ownership and minimum interfaces

The user refinement is stronger than either report's illustrative types. T3 owns durable user intent, conversation commands/events, permission decisions, thread membership and settlement requests. Its existing transaction/outbox delivers lifecycle intent. Hatchet persists lifecycle submissions, tasks and results; Go agent-runtime executes them and observes resources. Workspace bytes and native history live on retained workspace storage. Kubernetes owns actual PVC/Sandbox/Pod facts. A T3 execution-status projection is observational and rebuildable.

Do not implement A's `RootBinding.state` as a second authoritative allocation state machine. Do not interpret B's reference to existing runtime storage/fencing support as proof those APIs exist. L:29-41 and L:79-96 identify missing Go control and Hatchet integration seams. T3 may persist a root binding, accepted command references and replay cursor. Its existing domain state needs a workspace-wide monotonic intent version, including child work and scheduled wake. That version is conversational admission state, not another allocator database. A separate copy of every Kubernetes transition in SQLite would violate the requested ownership split.

The smallest proposed public-to-private boundary is:

```text
T3 bindRoot(thread, workspace, runtimeHandle)
T3 inheritChild(parent, child) within durable child creation
agent-runtime EnsureRunning(workspace, operationId, intentVersion)
agent-runtime QuiesceAndRelease(workspace, operationId, intentVersion, idleProof)
agent-runtime Observe(workspace)
agent-runtime PurgeWorkspace(workspace, explicitPurgeIntent)
worker Execute(owner, allocationFence, commandId, payloadHash, operation)
worker Replay(owner, incarnation, afterSequence)
worker Drain(allocationFence, intentVersion) -> activity and completion proof
```

`owner` identifies the actual thread/provider session and execution attempt. `allocationFence` contains stable workspace identity, allocation epoch, resource UID and worker incarnation. Kubernetes resource generation, allocation epoch and worker incarnation have different meanings; do not overload one `generation` number. A worker may restart inside the same Pod. Proposed wire messages are schema-validated DTOs, not Effect closures or SDK callbacks. The worker exposes files, VCS/checkpoints, PTY/scripts, browser/HTML preparation and provider session operations under one private protocol. Central Git/PR orchestration, model selection, settings, authorization and attachment publication remain central. B:68-72 correctly warns against relocating all of `GitManager`; `T3/apps/server/src/git/GitManager.ts:727` has central-state dependencies.

Workspace routing must become explicit where existing inputs contain only cwd. Two roots can use the same absolute path. A selected UI tab, project ID or environment ID cannot disambiguate concurrent calls. Use stable workspace/checkout references in file/search/media contracts, and derive the binding centrally for RPCs already carrying thread ID. Absolute sandbox `/tmp` paths still need a workspace identity. This is necessary contract work, not optional architectural polish. See B:76-105 and `T3/packages/contracts/src/project.ts:436`, `T3/apps/server/src/workspace/WorkspaceFileSystem.ts:142`.

## Lifecycle verdict and stale-delete objection

Adopt L's direct Sandbox with explicit external PVC and no volume claim templates. AS v1.0.3 accepts a full PodTemplate and passes explicit volumes into the Pod. Its generated PVC reconciliation only iterates VCTs, and attaches Sandbox ownership to adopted/generated claims. See L:7-25, `AS/api/v1beta1/sandbox_types.go:243`, `AS/controllers/sandbox_controller.go:1434`, and `:1639`. Claim lifecycle `Retain` retains the claim while deleting the Sandbox; it does not establish application data retention. Existing configured home is `emptyDir`, so the manifests are unsuitable unchanged. See `AS/extensions/controllers/sandboxclaim_controller.go:302` and `/home/node/workspace/config/clusters/shared/agent-environments/template.yaml:53`.

Hatchet persistence is not workspace persistence. Retain repository common directory, linked worktree administrative files, hidden checkpoint refs, untracked files, provider homes, copied inputs and relevant output files at stable mount paths. Retain the entire central T3 base directory independently. Never attach its writable SQLite directory to a worker. See B:108-111 and `T3/apps/server/src/config.ts:138`. Direct Sandbox release retains the external PVC. Purge is separate authorization and waits for all writers to be absent. Claims, pools and owner-reference stripping are unnecessary in v1. Warm pools may be added behind policy only after a real storage-adoption design is proven.

Reuse the Go Hatchet worker registration and generic control/process/files packages, not the OpenCode conversation engine. `AR/hatchetbridge/bridge.go:58` is an expiring per-run OpenCode provision/execute workflow with zero retries on those stages. It is not an existing retained root-workspace lifecycle. `AR/orchestration/engine.go:75` builds OpenCode-specific credentials/native identities. New finite T3 lifecycle workflows are required within agent-runtime; a new allocator product is not. See L:79-96.

L's keyed short transitions are the right shape, but serialization and a version in an immutable workflow input are insufficient to prove “latest intent.” Define how the mutation task reads the latest durable T3 admission version or a CAS-protected resource fence established from that intent. Wake events are hints. An old quiesce workflow cannot infer that its input is current because it was scheduled first. The pinned SDK has keyed concurrency and tenant-scoped shared names, but `QueueNewest` is not a correctness guarantee that stale work disappears. See `H/sdks/go/workflow.go:71` and `H/pkg/client/types/file.go:23`; verify deployed server semantics.

Use one workspace key with MaxRuns=1 for short resource mutations. If workflows differ, use the same tenant-scoped concurrency name. Do not hold that slot in a forever-running owner wait, and do not use cancellation of a task as retraction of an already submitted Kubernetes delete. Every stop/release consumes a proof bound to workspace intent version, allocation epoch, worker incarnation and all-member idle membership. If current intent cannot be established, automatic idle stop has no proof and must defer.

UID checks alone do not fence stale deletion of a resumed Sandbox with the same UID. Use mutation CAS against the observed resource version and desired intent fence, plus UID preconditions for deletion. A stale delete must never target a replacement allocation. A wake arriving after suspend/delete acceptance waits for the previous writer to disappear and current-incarnation readiness before dispatching new work. A wake arriving earlier invalidates the stop proof. The serialized mutations and dispatch barrier make either ordering safe; they do not require the illusion that a submitted delete can be canceled. This closes the under-specified check-then-delete interval in L:98-116.

Control readiness also needs repair before automated lifecycle. Existing `ready` accepts `Ready=True` without observed-generation matching; watch relist can accept replacement UID; `Scale` acknowledges a patch rather than old-Pod termination. See L:29-39 and `AR/sandbox/control.go:210`, `:233`, `:185`. Readiness is current Sandbox UID/generation plus worker handshake; stop completion includes previous Pod absence and writer exclusion. RWO alone is not a single-writer fence. Hard claim TTL must not masquerade as safe idle or silently terminate live approvals.

## Restart contract: conservative spike, proven production reattachment

Candidate A's conservative restart contract is the safe first gate. Candidate B's reattachment is the better eventual experience, but promises more than the inspected recovery code supports. T3 currently cancels process-bound effects after server loss and expires requests under central-process-loss assumptions. See A:74-76, B:139-141, L:44-58, `T3/apps/server/src/orchestration-v2/EffectOutbox.ts:483`, `ProviderRuntimeRecoveryService.ts:586`, and `T3/apps/server/src/serverRuntimeStartup.ts:400`. Skipping those routines does not establish reattachment.

The staged proposed contract is:

1. **The limited spike preserves conversation and files across restart, with explicit interruption of active attempts.** Graceful central shutdown blocks new admission, drains bounded work or explicitly interrupts it, fences worker execution and flushes acknowledged events before terminalizing unresolved attempts. Pending callbacks block ordinary safe-idle release. A forced maintenance shutdown that cancels them is an explicit interruption policy, not preservation. The synthesized production target requires proven same-worker reattachment; the spike must be labeled incomplete compatibility.
2. **After an ungraceful central crash, reconcile before dispatch.** Surviving workers are quarantined under the old execution epoch. Through agent-runtime, observe/fence or terminate the old writer and reconcile accepted/results/events before announcing the attempt interrupted. If the old worker is unreachable and writer absence cannot be proven, remain recovering/unknown and do not launch a replacement. A cannot safely mean “cancel SQLite now, kill worker later.” That creates continued edits after apparent cancellation.
3. **Enable central restart survival only after a dedicated proof gate.** Reattach to the same authenticated worker incarnation, recover command receipts, commit ordered event replay/cursor atomically, restore PTY/script watchers, reconcile request IDs, and refresh MCP credentials without restarting the owning provider session. Only then scope process-loss recovery to worker incarnation rather than central PID. This can preserve callbacks still held by the surviving worker. It does not serialize closures or resurrect them after worker loss.
4. **Worker/container/Pod loss interrupts process-backed activity in both stages.** Native history permits provider-supported later continuation. Expire approval cards whose callbacks died, invalidate PTYs/browser references, reject old-incarnation events and do not replay an approval response into a fresh provider process.

Even the conservative stage needs delivery receipts and dedupe. “Start accepted” is not “turn completed.” A lost ACK must not produce a second turn. Ordered worker events are acknowledged only after the central event transaction and cursor commit. A worker journal on its retained storage records execution delivery, not lifecycle ownership or a second conversation store. Arbitrary shell external side effects may have unknown completion after a crash. Replay only explicitly idempotent operations; reconcile Git push/PR results before retry. See B:61-63, L:101-107 and `T3/apps/server/src/orchestration-v2/EventSink.ts:527`.

## MCP and provider auth gate

A correctly identifies the current MCP token registry as in-memory and thread/provider-session scoped. Source inspection confirms the registry initializes a Map and chooses loopback from wildcard bind. See A:66-72, `T3/apps/server/src/mcp/McpSessionRegistry.ts:90`, `:104`, `:110`, and `McpProviderSession.ts:3`. Persisting central SQLite does not retain these registrations. A surviving worker's cached token fails after central restart, and localhost injected into a remote provider resolves inside its sandbox.

For the first conservative stage, use the central internal DNS MCP endpoint, issue each attached app child its own credential, and recreate credentials on later provider attach. Include the ACP stdio bridge in the image. Do not claim uninterrupted session reattachment from this path. Direct endpoint survival requires provider-specific proof that a live session can update headers/reconnect without dropping its callback-owning process. A control message to the adapter alone does not prove a SDK-configured client applies the change.

For the later survival stage, choose a worker-local MCP forwarding endpoint with hot central credential refresh if direct hot update cannot be proven across every supported provider. This is a handler in the same private worker, not another control-plane service. Give each actual thread/session a distinct local authorization identity and refresh its upstream token over the authenticated worker control channel. The proxy must preserve JSON-RPC/SSE, elicitation, request cancellation and session scoping, and bound retries during central outage. Do not switch a token globally across all children. Test that revoked or stale identities cannot be revived by refresh. Keep the direct endpoint as the simpler option where the full provider matrix proves live update; do not implement both blindly.

Native subagents need separate recorded native identities, but providers may execute their MCP calls using the parent provider's configured client. Neither A nor B proves every native subagent supports a separately configurable token. Enforce distinct app-owned child MCP credentials; preserve native owner attribution where the provider exposes it and explicitly gate unsupported per-native-child credential isolation. A blanket promise of unique native tokens would be unsupported.

Keep central provider declarations, OAuth/account selection and secret authority. Worker runtime probes report installed executable/version, model availability, usage/auth health and workspace-sensitive facts. Cache against image digest, provider instance and credential version; do not mark a stopped workspace provider unusable merely because no worker exists. Probe an allocated worker or a bounded policy-owned probe allocation where needed. Auth setup/refresh ownership must prevent two refresh-token writers and match the selected account for worker Git push and central PR APIs. See A:80-83 and `T3/apps/server/src/provider/Drivers/CodexDriver.ts:148`, `Drivers/ClaudeDriver.ts:120`, `Drivers/OpenCodeDriver.ts:261`. A finite ACP manifest and dedicated pinned all-built-in image are requirements; their licensed packaging, credentials and smoke support are unproven.

## Root lineage, checkpoints and product scope

Inherit execution binding in the same transaction as actual app-owned delegated creation, recursively. Do not allocate on every `thread.created`, and do not infer shared workspace from any parent/root lineage field. Ordinary conversation forks are new roots. Their initialization must deliberately define what happens to parent workspace state, including untracked files and provider fork support. Native subagents share the provider's existing workspace. See L:60-65 and `T3/apps/server/src/orchestration-v2/Orchestrator.ts:6536`, `:9329`, `SubagentProjection.ts:42`.

Candidate B is right about shared checkpoint truth. A private Git index protects the user's index; it does not snapshot a concurrently edited checkout or attribute edits to one agent. Extend shared locks for Git/ref mutations where appropriate, but do not promise isolated per-child checkpoints. Preserve rejection of file restore while another durable member shares the workspace. Conversation-only rewind remains separate. Make capture create-once for its checkpoint ID/OID because a lost result followed by edits and retry otherwise overwrites the checkpoint ref. See B:123-129, `T3/apps/server/src/orchestration-v2/CheckpointRestoreSafety.ts:36`, `T3/apps/server/src/vcs/GitVcsDriver.ts:1072`, and `T3/apps/server/src/orchestration-v2/CheckpointService.ts:397`. Workspace membership can change between restore admission and execution; the restore fence must include that change.

A provider-only prototype is not complete UI parity. Workspace files/search, Git/checkpoints, terminals, scripts, media descriptors, attachments, localhost preview, HTML local images and device launcher paths all need routing. Candidate B's feature table is the implementation checklist. Durable uploads/publication remain central; inputs are staged to worker paths; generated durable assets are ingested centrally. Worker filenames cannot be passed to central HTTP local-file responses. Browser execution sits beside app localhost; desktop native preview requires an explicit proxy or a worker-streamed renderer policy. Device authority remains central, with a real worker launcher bridge or an honestly unavailable capability. See B:76-93 and B:145-150.

Two product decisions remain gates, not invitations to invent a platform. Pre-thread project filesystem operations require an execution target. B:113-119's retained seed checkout is a reasonable single extra use of the same worker/lifecycle if preserving project browsing and clone flows is required. It must not share a writable repository with root checkouts. Do not silently replace those flows with selected-thread state. The second gate is root fork initialization: choose and test a consistent workspace copy/snapshot policy or explicitly bounded semantics. A pinned seed commit alone does not preserve current parent untracked edits. Neither decision needs another server or allocator.

## Ranked release blockers and proof gates

| Priority | Blocker | Required decision or executable proof |
| --- | --- | --- |
| P0 | Storage disappears under claim/template defaults | Direct external PVC, no transient owner refs/VCT; retain sentinel, native history, Git common dir and checkpoint through suspend/delete/replacement; prove old writer exclusion. |
| P0 | Stale stop/delete overtakes child/user/scheduled wake | Workspace intent version, latest-intent lookup, shared Hatchet mutation key, CAS resource fence and dispatch barrier; inject stop-after-wake and delete-after-resume races. |
| P0 | Central recovery cancels a surviving writer or spawns duplicate work | Implement conservative recovery quarantine/fence first; cut crash at accept/start/result/central commit boundaries; prove no continued writer after terminalization. |
| P0 | MCP reconnect silently breaks surviving provider | Private endpoint and scoped attach credentials for stage one; prove hot header update or worker proxy plus refresh before enabling stage two. Include actual approval/elicitation. |
| P0 | Local cwd routes to central or another root | Two workers with identical paths/ports and central trap files; verify file/edit/Git/terminal/browser/media/HTML and child routing. |
| P1 | Settle drops scripts, children or terminal activity | Durable script receipt/completion barrier, all-member idle proof, failed/hung-script policy and new-work admission race tests. Sidebar settled is insufficient. |
| P1 | Worker dies with checkpoint/ref mutation or external shell action | Create-once checkpoint OID; same-command retry; explicit unknown/interrupted results for non-idempotent effects. |
| P1 | Built-in image and auth/catalog coverage assumed | Codex plus an SDK-owned provider first, then all built-ins and finite ACP entries with native resume, account selection, MCP, approval and capability reports. |
| Decision | Project seed, ordinary fork contents, desktop/device parity | Pick explicit scope before saying existing UI behavior is preserved; use one worker protocol and capability declarations. |

The first prototype should prove one end-to-end vertical slice, not attempt every UI migration at once: central single-writer storage, two independent roots, one app child, direct retained PVC lifecycle, Codex plus Claude or Cursor, scoped MCP and an approval, file edit/checkpoint, explicit conservative central restart, and worker replacement. Broaden the provider and feature matrix only after that contract holds. Central restart survival gets its own gate after MCP refresh and callback reattachment are exercised under actual process cuts.

The final architecture can keep infrastructure invisible while honestly showing existing execution status during allocation/recovery. Hidden pools do not justify hidden data loss, a success receipt at command acceptance, or an answerable approval whose callback has died. The reports give a sound boundary choice and concrete missing seams. They do not establish deployed storage behavior, all-provider auth compatibility, current Hatchet server concurrency semantics, or implemented restart survival.

## Follow-up critique of the synthesized report

Reviewed `/home/node/.t3/worktrees/agent-runtime/t3-f4b23110/docs/research/t3-sandbox-architecture.md` too. Its worker-local MCP proxy, retained external-PVC direct Sandbox, central single-writer store, native-child identity caveat and Hatchet authority split are coherent. The proxy is a sound target choice that avoids assuming live SDK header replacement. It remains an unimplemented protocol whose token refresh and callback behavior require proof.

The highest remaining fixes are concrete:

- At synthesis:126 and :200-204, identify the source of the latest workspace admission revision and fence the final mutation atomically. A workflow input and UID check alone cannot reject stale deletion of a resumed same-UID Sandbox. ResourceVersion CAS plus intent/epoch validation and the dispatch barrier are required. Parent reports this fix accepted for incorporation.
- At synthesis:59-62 and :159, distinguish allocation epoch, Kubernetes metadata generation and worker incarnation. At :122, separate workflow definitions need the same tenant-scoped concurrency name, not merely equal key expressions. Verify deployed Hatchet semantics.
- At synthesis:173 and :289/:295/:299, keep production reattachment acceptance separate from the allowed interrupting spike. The production gate can favor stronger feature preservation, provided same-worker approval survival is demonstrated. The spike must fence or reconcile old writers before terminalizing their runs and must not claim target parity.
- At synthesis:181-185, make proxy reauthorization per thread/provider session, with revocation/TTL and existing upstream MCP operation reconciliation. Refreshing a token does not recover process-local MCP transport state or a lost side-effecting tool response. Test lost response after thread creation specifically.
- At synthesis:70 and :235, keep ordinary root-fork content semantics separate from seed-based new-project initialization. A seed commit does not preserve untracked parent edits, and a checkpoint does not establish a consistent live shared-workspace snapshot. Treat the fork policy as an explicit decision gate.
- At synthesis:237-241, browser profiles must not quietly exclude a required built-in provider from the dedicated all-built-in image. Browser capability can vary by policy; the finite provider manifest remains required. Auth compatibility remains visibly gated as :245 already states.

Preserve the synthesis distinction at :159 between durable provider turn admission and final completion. The provider-start outbox effect may complete when admission returns a stable native reference; final run completion arrives via committed events. Checkpoint/script completion has different semantics and must satisfy its own release barrier.
