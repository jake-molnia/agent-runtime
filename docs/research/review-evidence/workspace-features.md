# Candidate B: put filesystem-bound execution beside the checkout

This is a design review, not an implemented or tested migration. Source references below are relative to `/tmp/t3code-sandbox-research`, pinned at `580948708b66f2a971199670f76cb6b43119e9a4`. The existing repo uses `cwd` as both a filesystem address and an implicit environment identity. Splitting execution across sandboxes requires separating those concepts before moving a single process.

My recommendation is a small execution worker in each allocated sandbox, built from the same T3 source revision. It owns provider runtime instances and the complete local operations that require the checkout, process table, PTY, native search index, or browser. The central T3 server retains SQLite, orchestration, projects, permissions, settings, credential selection, durable attachments, PR metadata, and public HTTP/WS/MCP. The worker is not another T3 server: no public UI, pairing, SQLite projection store, project catalog, or orchestration engine. A single authenticated internal protocol carries semantic operations and streams. The existing Go agent-runtime plus Hatchet owns durable sandbox creation, allocation, retained storage, lifecycle, stop/resume, generation fencing and connection routing. Reuse its control/files/processes/tailnet/artifact capabilities. T3 stores only an opaque runtime execution binding on the root thread, inherited by descendants; it must not add a replacement allocator, reconciler or lifecycle database. The TypeScript sandbox worker owns T3 execution services; the Go runtime should not grow T3 Git or terminal semantics.

A remote implementation of Effect `FileSystem` and `ProcessRunner` is a useful limited implementation tool. It is not the architectural boundary. Direct Node filesystem operations, `fff-node`, `node-pty`, Playwright, and provider SDK-owned subprocesses escape it. More importantly, HTTP media responses currently return live local descriptors, UI RPCs lack destination identity, and checkpoint/settlement safety reasons about one machine. Replacing two services cannot repair those semantics.

## Start with how callers should use it

These are proposed interfaces; use Effect Schema brands and derive inputs from existing contracts in implementation.

```ts
// Stable across pod replacement. An allocated pod is never a WorkspaceId.
type WorkspaceRef = {
  workspaceId: WorkspaceId;
  checkoutId: CheckoutId;
};
type BoundExecution = {
  workspace: WorkspaceRef;
  allocationId: AllocationId;
  generation: AllocationGeneration;
};
type ExecutionOwner = {
  threadId: ThreadId;
  providerSessionId: ProviderSessionId;
  mcpSessionId: McpSessionId;
};

interface ExecutionWorkspaces {
  // Resolves the persisted binding; recursively delegated children inherit it.
  forThread(input: { threadId: ThreadId }): Effect<WorkspaceRef>;
  // Delegates readiness to agent-runtime/Hatchet; checks worker protocol version.
  withReady<A>(input: {
    workspace: WorkspaceRef;
    use: (worker: WorkspaceExecution) => Effect<A>;
  }): Effect<A>;
}

interface WorkspaceExecution {
  readonly files: WorkspaceFiles;
  readonly vcs: WorkspaceVcs; // Existing GitVcsDriver/CheckpointStore-shaped methods.
  readonly terminals: WorkspaceTerminals;
  readonly preview: WorkspacePreview;
  readonly providers: WorkspaceProviders;
  ensureInput(input: { attachment: AttachmentId; digest: Sha256 }): Effect<WorkerFileRef>;
  inspectActivity(): Effect<WorkspaceActivity>;
  beginDrain(input: { transitionId: TransitionId }): Effect<DrainState>;
}

// No raw cwd selects a worker. Resolve a checkout-relative path on that worker.
type WorkspaceFileRef = { workspace: WorkspaceRef; path: WorkspaceRelativePath };
// A sandbox /tmp report is explicitly sandbox-local, never a central host path.
type WorkerFileRef = { workspaceId: WorkspaceId; path: WorkerAbsolutePath };
```

Example usage stays short. The central checkpoint effect resolves the thread's binding, calls `worker.vcs.captureCheckpoint({ checkoutId, checkpointRef, operationId })`, and commits the resulting checkpoint event centrally. A file panel sends `{ workspace: thread.workspace, relativePath }`; central authorization checks the workspace grant and calls `worker.files.readFile`. The worker derives the real root from `checkoutId`, performs canonicalization and no-follow checks on its own filesystem, and returns bytes plus metadata. A terminal RPC already has `threadId`, so its central adapter resolves the binding without another public selector.

The wire envelope carries `{ workspaceId, allocationId, generation, operationId }`, validated by the worker. The normal feature API should expose the stable reference, not require every caller to pass the generation. The central execution client obtains the generation after readiness and never silently retries a mutation into a newer generation. Streams have stream ID, sequence, and resume cursor. PTY/process identities are opaque worker handles, not central PIDs.

Use the existing runtime/Hatchet operation identity and durable workflow support where available, rather than a parallel lifecycle journal in T3. Keep feature operation IDs only where a lost response makes replay consequential: provider turn start, terminal open/restart, checkpoint capture, worktree creation/removal, clone, push/PR creation, and script launches. Ordinary read retries do not need an operation journal. Mutating operations record a result on retained workspace storage before acknowledgement, with explicit unknown/interrupted results where shell side effects cannot be inferred.

Do not blindly relocate `GitManager`. Likewise, keep project script selection central and execute an explicit resolved script request on the worker. ## Identity and storage decisions that cannot be postponed

### A path is not a destination

Two sandboxes can both have `/workspace/repo`. Existing `projectSearchEntries`, `projectSearchContents`, `projectListEntries`, `projectReadFile` and `projectWriteFile` carry only cwd. The central server cannot infer which sandbox from authentication, project ID, connection, active UI tab, or the shared environment ID. Multiple tabs and MCP callers act concurrently. Do not infer a thread from “currently selected thread.”

Preferred fix: add a `WorkspaceRef` to execution requests and thread projection; keep user-facing project and thread UI unchanged, with shared client-runtime wrappers attaching the reference. Terminal/preview calls already contain thread ID; derive the ref server-side there. `draft-workspace-file` assets at `ws.ts:2713` have no thread and need an explicit draft/seed workspace reference. Repository-wide browser and PR UIs need the same explicit project-vs-thread target decision.

Alternative with less contract churn: assign each persistent workspace a globally unique, stable worker mount path such as `/workspaces/<workspace-id>/repo`, retain it across replacements, and let central routing map the registered prefix to a workspace. This preserves cwd-only call shapes. It still needs thread-to-workspace mapping, a target for absolute `/tmp` reads, canonical path validation on the worker, project draft roots, and scoping of every cache. It turns path syntax into an undocumented routing protocol and cannot route `/tmp/report.png` without another selector. I would choose explicit identity despite the one-time client changes.

`EnvironmentId` remains the central T3 environment. `WorkspaceId` is persistent execution/storage ownership. `AllocationId`/generation select the current worker. `CheckoutId` identifies a checkout within the workspace, needed if worktree MCP remains available. Thread, provider session/thread, MCP session, checkpoint scope and terminal IDs remain separate. Parent and child inherit only workspace/checkout binding by default, never provider or MCP identity.

### Preserve the entire repository, not just visible files

For independent top-level threads, give each workspace its own repository and `.git` storage. A linked worktree on a PVC with `.git` pointing into a central or ephemeral checkout fails after replacement. The Git driver resolves the common directory and places private indexes there (`GitVcsDriver.ts:819`); hidden checkpoint refs live in that repository (`:1072`). Retain the common directory, all linked worktree directories, submodule repositories, untracked/ignored files, provider resume directories, input attachments, logs and relevant browser/download storage. Stable absolute mount paths avoid rewriting linked-worktree administrative paths and provider resume paths.

A Git commit, clone, tar of tracked files, or checkpoint alone does not preserve a running workspace's data. A generic retained volume is the default proposal. Snapshot/export is an alternative only if it covers the complete directory graph and has a verified consistency point. Storage loss cannot be repaired from central SQLite checkpoint metadata alone. Keep central T3's whole data directory on its original persistent volume and its writer central; never mount that writable database directory into workers.

### Project operations before a thread exists

This needs an explicit product decision. Current project creation normalizes an existing directory, file browsing runs with project cwd, GitManager obtains project identity from cwd, and settings/scripts load from the project tree. “Allocate on first turn” leaves those paths without an execution target.

Smallest complete proposal: a project stores a repository clone specification and a retained project seed checkout reference. A seed has a workspace ID but no provider thread. Use the same worker executable and allocation API for temporary seed operations; it runs no UI or T3 server. New top-level threads receive distinct retained workspace IDs and independent checkouts initialized from a pinned seed commit/config. Children share the parent's workspace recursively. Project-scoped reads/clone/template editing route to the seed; thread reads route to the thread workspace. The seed stops when its finite operation finishes. Pool policy remains hidden.

This is an extra allocation use case, not an extra service. If minimal scope instead removes pre-thread filesystem browsing and local-folder project creation, say so in the UI and acceptance criteria. Do not silently use a selected conversation's checkout for project-wide operations; it changes branch/settings semantics and breaks concurrent drafts. A central read-only project mirror is another option, but it preserves two execution localities and must never become the implicit source of thread truth.

## Shared child execution and checkpoint truth

Existing app delegation copies parent's `projectId`, branch and worktree path (`mcp/OrchestratorMcpService.ts:2138`-`:2156`). Extend that operation to inherit the persisted workspace binding in the same central transaction that creates the child. Derive recursively from the actual parent, not a caller-supplied root-thread string. Native subagents spawned within a worker naturally share filesystem/network; record their owner identity for MCP authorization, activity and stop decisions.

The shared checkout is intentionally concurrent. T3's checkpoint capture uses a private Git index, which protects the user's index; it does not isolate file edits or create a point-in-time filesystem snapshot. A parent snapshot may include sibling edits. Files can change during the Git staging scan. The existing `CheckpointService` mutex serializes its own capture/restore operations, not provider writes, user shell writes or file-editor writes. `workspaceLease.ts` coordinates startup/removal only. Neither is a transaction covering the workspace.

For the first version, preserve honest current semantics: checkpoints describe the shared checkout observed around completion, not changes attributable to one agent. Keep conversation-only rewind available. Preserve file-restore rejection whenever another durable thread shares that workspace, including archived nondeleted threads if following current safety. Do not weaken this rule merely because both threads share a root lineage. A future root-workspace restore could quiesce every member and rewind all affected metadata as an explicit group operation; that is additional behavior, not a small safety fix.

There is a new concrete replay hazard. `CheckpointService.capture` calls capture unconditionally (`:397`), and the driver overwrites the ref (`GitVcsDriver.ts:1072`). If Git finishes but central receives no response, a retry after more edits can silently replace the same checkpoint with different content. Make ref capture create-once for a stable operation/checkpoint reference; return existing OID on retry. Persist OID and operation result. Use compare-and-swap ref creation or a worker operation record and serialize by repository/workspace. Do not return a fresh timestamp with a silently new tree under the old checkpoint ID. Baseline capture already checks existence (`CheckpointService.ts:279`), but turn capture does not.

## Stop, settle and restart

The central thread “settled” state is not sufficient evidence that compute is disposable. Current cleanup intentionally leaves busy terminal commands running and detaches the settle completion effect. New lifecycle state must cover the entire workspace membership, including native background work, delegated children, pending provider approvals/user requests, queued turns, active file/Git operations, setup/settle scripts, uploads into worker storage, and interactive browser activity.

Proposed policy separates idle stop from explicit settle. Idle stop does not kill a foreground terminal, live approval, active preview interaction or task that promises to wake a provider. An abandoned dev server can be stopped under an explicit documented idle policy; port existence alone is not “work pending.” Explicit root settlement requests drain, runs the configured settle action, then stops remaining workspace processes under the agreed policy and releases compute while retaining storage. A child settlement does not stop the shared allocation while any sibling/root needs it.

Have the existing Hatchet lifecycle workflow persist its transition ID; supply a settledAt-derived script operation ID from T3. T3 reports semantic blockers and requests stop/resume through agent-runtime. It does not run a second allocation reconciler or persist a competing sandbox state machine. Block new operation admission while entering drain, recheck memberships centrally and worker activity under the same generation, then stop. A new user turn cancels drain before destructive stop or waits for stop completion and reallocates afterward. The UI should report stopping/resuming and failed settle scripts using existing status mechanisms where possible. Failed or hung settle commands must produce an explicit failed stop attempt or a separately defined timeout policy; “settled” must not imply script success.

Central restart with live worker: resolve the opaque binding through agent-runtime, reconnect to the existing generation, list/reconcile provider sessions, PTYs, scripts and pending requests, replay durable event cursors, and reattach watchers. Worker continues callbacks it still owns. Do not create a second terminal/script/provider turn because central lost its in-memory map. Central's SQLite remains the command/event authority; worker operation results are execution receipts, not a second thread database.

Worker process/pod restart: open descriptors, PTYs, browser DOM references and live approval callbacks are gone. Retained files/provider session data can restore the same conversation, not the same process continuation. Mark process-backed operations interrupted or lost, invalidate terminal/browser process handles, report pending approval request interruption honestly, and resume only through provider-supported persisted session paths. On replacement, reject stale frames, old attachment handles and delayed control messages from the old generation. Git checkpoint references, provider resume files, copied inputs and finished assets remain usable.

No general exactly-once guarantee exists for arbitrary shell scripts: a script may call an external service then die before its local completion marker. Track started/completed/interrupted durably; replay only commands explicitly safe to replay, otherwise show unknown completion. For Git push/PR creation reconcile remote results before retrying.

## Preview and user-device locality

A browser reading `localhost:3000` must share the app's network namespace or use an explicit proxy. Moving only shell commands breaks that invariant. Moving browser launch to worker preserves it and also preserves provider access to downloaded files and screenshots. Keep permission/ownership of human vs agent browser tabs central, with the worker owning Playwright page objects and local profile files. Namespace profiles by workspace and thread/automation owner as appropriate. Existing worker generation reconnect may retain pages; worker death invalidates pages and element references.

Desktop's native webview is a separate case. `ServerBrowser.createTab` may connect to desktop rather than create a headless page. The user's laptop `localhost` is not the worker. Minimum fork policy should use streamed server-browser rendering for sandbox-local targets across desktop, web and mobile. If retaining native rendering, add a signed proxy with HTTP+WebSocket routing and stable target identity, and test Vite HMR/cookies/redirects. An external arbitrary URL may still use a desktop renderer if its automation contract remains valid. Do not announce native parity before that path is tested.

Device tools are also separate from worker browsers. Central DeviceService represents user device hosts and consent. `device_open` currently returns central filesystem launcher/config paths. A worker bridge has to install a runnable command there and translate authenticated session/device target requests to the central device service, including artifacts that cross machines. Existing quick-start guidance explicitly says remote build/install and Metro forwarding are the agent's responsibility (`mcp/toolkits/device/handlers.ts:64`). Running Linux workers does not supply a Mac simulator. If this bridge is not in the first fork, remove the capability and return a specific unsupported explanation; never give a central-only executable path to the agent.

## Minimal module changes and delivery proofs

1. Add an opaque root-thread-to-runtime binding in existing T3 conversation storage/projections and explicit workspace references for feature routing. Keep durable allocation/lifecycle records solely in agent-runtime/Hatchet. Extend cwd-only contracts at one shared client-runtime call boundary; thread-based RPCs resolve centrally. Migrate paths to stable checkout metadata and keep EnvironmentId unchanged. Proof: concurrent requests with identical cwd hit different test workers; nested app children inherit one workspace while keeping distinct sessions.
2. Add one private worker entry point from the same server package, assembled from execution services only. Initially host workspace files/index, VCS/checkpoints, PTY, process services, preview/HTML execution and provider runtimes. Add central remote implementations of those semantic service contracts. Proof: launch local test worker as a subprocess with central cwd containing trap files; every feature uses worker paths and central traps remain untouched.
3. Split durable asset publication from local access. Retain upload/claims/publication centrally, copy scoped inputs, relay live workspace reads, ingest generated HTML/screenshots/download attachments when referenced in conversation. Proof: stop worker and still render published conversation assets; stale live workspace URL fails explicitly or wakes through policy, never reads central disk.
4. Keep Git/PR orchestration and repository identity central; proxy worker local VCS operations and small instruction reads. Persist identity needed for dormant PR watches. Proof: commit+push+PR on a disposable repository, dropped response reconciliation, all checkpoint objects present after replacement, submodule/worktree metadata valid without central paths.
5. Integrate durable script receipts and T3 activity/drain reporting with the existing Hatchet workspace lifecycle, replay and fencing. Proof: lost central connection leaves one script/PTY/provider; worker death yields interruption; child/approval activity blocks stop; completion precedes compute release; fresh turn during drain either cancels drain or resumes after completed stop.
6. Cover preview and device policies in contracts/capabilities. Proof: web/desktop/mobile request shape parity, worker-local port collision isolation, browser restart behavior, actual device bridge if enabled. UI verification is a later authorized implementation activity, not performed here.
