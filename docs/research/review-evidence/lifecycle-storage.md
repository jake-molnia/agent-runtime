The smallest credible v1 is a central T3 conversation single writer plus agent-runtime Go workers using Hatchet durable lifecycle workflows and direct Agent Sandbox resources, each mounting a separately managed retained PVC. A PV reclaim policy of Retain is not an adequate substitute for retaining the PVC. It can leave released underlying storage after the PVC object is deleted; it does not transparently bind a replacement Sandbox to the same claim and paths. Neither claim/template VCT nor expiry Retain meets the durable workspace requirement.

Recommended direct path: provision PVC `t3-workspace-<workspaceId>` once, record its UID, and mount it at stable paths in a `Sandbox` named from `<workspaceId, allocationEpoch>`. Leave `volumeClaimTemplates` empty; set service true, explicit non-token pod identity and pinned worker image. The agent-runtime lifecycle workflow owns PVC deletion only for an explicit workspace purge, never ordinary settlement. Do not make PVC owner references point to a transient Sandbox, claim, Pod or pool. Retain the central T3 volume independently too. Use a storage mode and driver that actually support intended remounts; RWO does not by itself prevent two Pods on the same node writing. Require the previous Pod to terminate/detach before a replacement writer is activated; RWOP where supported is a useful extra constraint.

This adds direct-resource methods to generic Go Control, not a new orchestration engine. It avoids one template and zero-replica pool per root. A claim-based fallback can use a per-root template with the external PVC explicit in podTemplate and a pool with replicas zero, whose schema permits zero at `AS/extensions/api/v1beta1/sandboxwarmpool_types.go:39-51`. It works structurally but adds resources solely to overcome a claim API restriction. Do not implement owner-reference stripping during teardown: it creates a GC race and fights the controller's adoption reconciliation.

Warm allocation alternatives are materially different products: a shared RWX filesystem mounted in generic warm Pods with a strict per-workspace boundary, or an explicitly designed late-binding storage mechanism. Both need isolation/concurrency proofs. Patching a running warm Pod to attach a root PVC is not a supported generic claim feature. Cold direct Sandbox is the minimal first release and still uses Kubernetes Agent Sandbox.

## Generic Go Control gaps

`AR/sandbox/control.go:64-137` is useful for stable claim creation, ownership/spec hash checks and timeout recovery. Delete uses claim UID preconditions (:170-176), expiry patches test UID (:178-181), and Scale checks claim UID/binding before patching the Sandbox UID (:185-207). Keep those patterns, not the OpenCode engine.

Blockers for this lifecycle:

1. `ready` accepts `Ready=True` without observedGeneration checks (:210-231). After Running/Suspended or template mutations, it can accept stale readiness. `Scale` only acknowledges the patch, not terminal suspension. Add explicit Observe/WaitForMode using resource UID, target generation, observed conditions and worker handshake. Running means current Pod+worker ready; suspended means controller-observed suspended and old Pod gone. Claim readiness cannot replace Sandbox checks.
2. `Lease` stores claim UID but no Sandbox UID, Pod UID or worker incarnation (:35-43). `Resolve` gets a Sandbox by arbitrary name and waits ready without proving claim ownership (:139-157). `Attach` checks claim UID but does not wait claim readiness or verify the dependent owner (:159-168). Store and verify resource identities and authenticated allocation handshake; DNS alone is not identity.
3. `waitReady` verifies UID on watch events but a watch close/expiry leads to a GET whose UID is not compared against the initial UID (:233-255). A delete/recreate during that gap can be accepted. Keep the initial UID across relists and fail replacement.
4. `ClaimWithSpec` requires a future expiry (:72-79); retry of an existing claim returns the original expiry (:120-126). Idle suspension does not disable the deadline. Hard expiry can kill pending approvals regardless of T3's safe-idle decision. For direct Sandbox v1 omit automatic hard expiry by default and let durable desired-state reconciliation suspend safely. If an operational TTL is required, renew with margin and report forced expiration as runtime loss, never safe suspension. A finite TTL cannot guarantee indefinite approval preservation across central outages.
5. `Find` returns neither expiry nor Sandbox UID (:314-325); inventories key claims only by name, not namespace (:290-310). These are insufficient authoritative allocation records across namespaces. Direct-resource control should return a discriminated handle with namespace, name, UID, generation, observed mode and Pod identity. Keep claim support as a separate handle kind if needed.

Proposed minimal control signatures: `EnsureSandbox(ctx, key, pinnedSpec) -> SandboxHandle`; `Observe(ctx, handle) -> Observation`; `SetMode(ctx, handle, expectedGeneration, Running|Suspended) -> newGeneration`; `DeleteSandbox(ctx, handle) -> accepted`; `WaitAbsent(ctx, handle)`. PVC ensure/observe belongs alongside these control methods or the agent-runtime lifecycle workflow. None decides whether a T3 thread is safe to stop.

## T3 state and existing recovery assumptions

T3 already supplies the durable command boundary. `T3/apps/server/src/orchestration-v2/EventSink.ts:527-585` reserves a command receipt, appends events, applies projections, enqueues effects, records receipt and cancels effects before publishing. Reuse this transaction and outbox; do not add a competing central event database. SQLite is configured with WAL and foreign keys at `T3/apps/server/src/persistence/Sqlite.ts:15-25`. Mount the whole configured base directory, not only `statev2.sqlite`: `T3/apps/server/src/config.ts:138-166` places attachments, settings, environment ID, secrets, terminal/provider logs and browser artifacts under stateDir, plus caches and worktrees elsewhere under baseDir. Keep the central `environment-id` stable and do not put central state.sqlite on worker PVCs.

The existing recovery is explicitly tied to process loss of the central server:

- `EffectOutbox.ts:117-134` marks provider start/interrupt/steer/restart and runtime-request.respond process-bound, while checkpoint and detach/rollback/cleanup/delegation stop are replay-safe.
- `EffectOutbox.ts:483-509` cancels all pending/running process-bound effects on process loss and requeues running replay-safe effects.
- `ProviderRuntimeRecoveryService.ts:228-238` selects pending non-message requests for expiration/cancellation. At :586-627 it assumes all provider processes are gone on startup/shutdown, clears native background rosters and stops provider sessions.
- Claude and Codex adapters advertise `pendingRequestsSurviveRestart: false` in `Adapters/ClaudeAdapterV2.ts:179` and `Adapters/CodexAdapterV2.ts:256`; Claude's pending request state is an in-memory Ref/Map at :3068. Persisting a request card does not persist its live callback.

These assumptions must change for a worker that remains alive across central restart. Scope process loss to an execution incarnation, not to central PID. On central restart, keep worker sessions and request cards reconciling until the old worker authenticates with its allocation epoch and incarnation and returns a snapshot plus replay. Attach to that incarnation before dispatching pending commands. Only worker/process loss expires callbacks and interrupts corresponding runs. A transient transport disconnect must not invoke existing global process-loss recovery.

If the worker actually restarts, native history on PVC permits a supported provider resume; it cannot resurrect an in-flight SDK closure, approval callback, PTY or native background task. Preserve durable conversation and queued messages, mark the active attempt interrupted/failed with a reason, expire process-bound request cards, and use the existing explicit restart-continuation policy for a new attempt. Do not replay an approval response to a new session. Distinguish worker incarnation from Pod UID because a container or worker process can restart inside the same Pod.

## Minimal persistence split with Hatchet authoritative

The explicit architecture requirement is to build on agent-runtime and Hatchet, not install a second lifecycle controller/database in T3. T3 SQLite owns conversations, projections, command receipts and their delivery outbox. Hatchet owns allocation/init/quiesce/release workflows and their task inputs/results/replay state. Kubernetes owns actual Sandbox/PVC/Pod state. The retained workspace volume owns repo bytes and native harness state. These are different authorities, not duplicated copies of desired allocation state.

T3 needs only `thread_execution_bindings(thread_id PK, workspace_id, root_thread_id, lifecycle_handle)` plus remote event cursors/accepted command references and a user-facing execution-status projection. Create the binding in the existing thread transaction. Status projection is observational and rebuildable from agent-runtime, never an independent reconciler. Existing outbox delivers `EnsureRunning`, `Quiesce`, `Release` and worker execution requests using stable effect IDs. Preserve existing domain settlement/workflow rows for the T3 script barrier where appropriate; lifecycle decisions consume them.

Hatchet lifecycle input/output contains workspace/root identity, action/command identity and monotonic intent version, pinned resource/image/mount policy, allocation epoch, PVC and Sandbox namespace/name/UID, target generation, worker incarnation, initialization completion and quiescence evidence. These are durable workflow payloads/memos/results, not proposed new T3 allocation tables. Allocation observations must still come from Kubernetes and authenticated workers after replay. Stable resource naming from workspace+epoch lets a failed task rediscover resources even when its result was never persisted. Do not use a new Hatchet workflow-run ID as the workspace identity each time a thread wakes.

A worker-side command/event journal on retained workspace storage serves remote execution delivery only. It records command ID/payload hash, accepted/started/result, incarnation, ordered event sequence and acknowledgement. This journal cannot resurrect provider callbacks after worker process death. It is not a T3 database or a second lifecycle authority. Reuse Hatchet persistence for lifecycle results; keep high-volume provider token/events on the direct worker-to-T3 stream, not Hatchet workflow history.

## Authoritative transitions, acknowledgements and fences

Hatchet lifecycle intent is authoritative for allocation; Kubernetes status and worker observations are facts consumed by the agent-runtime workflow. T3 is authoritative for whether conversation work exists. `running -> quiescing -> suspended` is a protocol, not a UI event handler. New work commits an EnsureRunning lifecycle command and execution effect through T3’s outbox, carrying a monotonic conversation intent version. At any crash point, the Hatchet workflow replays its durable intent and observes resources by immutable UID. Stable allocation key + spec hash makes create retries converge. Resource absence is not conversation deletion.

1. Before dispatch, persist work and ensure current workspace epoch is running. Bootstrap/handshake verifies the PVC/workspace identity, image/protocol, resource UID and worker incarnation. K8s Ready only permits attempting the handshake.
2. Send a stable command ID with payload hash. Worker first records acceptance; duplicates with same hash return the current result, different hash is a protocol error. Accepted means durably received; started means execution begun; completed means result committed. An outbox effect must not succeed merely because a websocket send or acceptance happened.
3. Worker emits ordered events keyed by workspace/epoch/incarnation/sequence. Central commits dedupe, events/projections and cursor advancement together, then acknowledges. Disconnect after commit before acknowledgement produces harmless replay. A gap requires replay/snapshot repair, never skip. Late events from superseded allocations must not mutate active attempts.
4. Cancellation is a durable intent with its own command identity targeting the exact attempt/command/incarnation. It can precede a start; the worker must persist a tombstone so a delayed start is rejected. Existing Stop's `delegated-tasks.stop` outbox effect (`EffectOutbox.ts:109-125`) remains recursive and replayable. Stop a child process/session, not its shared Pod. Root cancellation can stop descendants, then quiesce; parent settlement alone does not cancel healthy children.
5. A crash between process creation and a durable started/result record cannot be given magical exactly-once semantics. Within one surviving worker incarnation, dedupe plus process registry prevents duplicate spawns. After worker loss, mark uncertain arbitrary side effects interrupted and apply provider continuation policy; checkpoint/ensure operations can be replayed only where explicitly idempotent.

## Safe idle, settlement and scheduled wake

Do not decide liveness from the root provider status or `thread.settled`. Safe suspend requires the entire workspace binding set to have no active/starting/queued execution that is runnable, no pending process-bound approval/input/elicitation callback, no live native background task, no app-owned child still executing, no setup/checkpoint/rollback/settle script, no file/Git write, and no active user terminal command or preview process that policy promises to keep. Idle shells can be closed; a dev server is not an idle shell. Unknown/disconnected liveness is not proof of idle. Use aggregate queries against existing projections/outbox, plus a worker quiescence response for processes the projections cannot observe.

Settlement race exists in current source. `ThreadSettlementService.ts:553-583` checks settled state, closes idle terminals, checks filesystem and rereads the thread, starts the settle script, records an in-memory timestamp, then forks completion detached. This protects against some reengagement but has a final check-to-start window, no durable dedupe across central restart, and no completion barrier for deleting compute. The comments explicitly preserve running terminals. Do not make `thread.settled` immediately delete/suspend the Sandbox. Turn settle cleanup into a durable operation; await actual script completion and workspace-wide quiescence before releasing compute. A child settlement must not run a destructive shared-worktree script concurrently with a sibling or root. Defer shared destructive cleanup until the whole workspace is quiet, or require scripts to be scoped/non-destructive by explicit policy.

Quiesce should carry intent_version and a barrier command. Worker stops accepting new side effects at that version, flushes results/history/journal and responds with process/callback counts. T3 validates the unchanged conversation version and all descendants/effects; the agent-runtime workflow consumes that bounded quiescence proof and checks worker/resource generation before requesting suspension. New work cannot execute until EnsureRunning completes, even if a prior proof races with a suspend patch. A wake arriving during quiesce invalidates the barrier and restores running before dispatch. If a wake arrives after the Kubernetes suspend patch, wait for termination and new current-incarnation readiness before executing. An old suspend outbox item must fail its intent-version check rather than suspending new work.

`ScheduledTaskService.ts:781-830` already creates a deterministic webhook delivery command ID and chooses `threadLaunch.launch` for an unbound task or `threadManagement.sendToThread` with mode queue for a bound task. Hook allocation wake into those shared services/effect paths, not the browser handler. A bound task resumes its existing workspace/conversation; an unbound launch creates a new root and workspace. Persisted future schedules do not need keepalive compute. Trigger execution holds the same workspace liveness barrier as user input. Scheduled launch dedupe must keep the same workspace on retry; use existing command receipts.

Release and purge differ. Settle can suspend or delete compute once safely quiescent, but retains workspace PVC and conversation. A later message creates/restarts compute for the same binding. Only an explicit permanent workspace purge deletes PVC data after all users of the binding and compute have been removed. Archive/delete of one child is not authorization to delete the root workspace.

## Required focused proofs before enabling lifecycle automation

- Resource ownership integration: create explicit externally owned PVC + direct Sandbox with no VCT; write sentinel/history/git checkpoint; suspend/resume, delete Sandbox, create replacement and read all three. Inspect owner references before/after. Repeat claim+VCT separately to prove it is intentionally not the durable path. No cluster operations were performed for this report.
- Control readiness tests: stale Ready from previous generation, UID change during watch relist, claim ready while Sandbox generation stale, Pod alive during suspension, worker process restart within same Pod, omitted service fails diagnostic rather than hangs.
- Root/child tests: independent roots get different PVC/binding; descendants at depth three inherit; ordinary conversation fork gets new binding; native subagents retain thread identity without new allocation. Child cancellation cannot kill sibling/root.
- Crash-cut tests around every durable boundary: create timeout before UID stored, worker accepted before central ack, central event commit before ack, command start before journal result, central restart while callback live, worker restart while callback pending, cancellation before delayed start. Assert no duplicate provider turn; show interrupted state for ambiguous process loss.
- Settlement tests: delayed settle script plus immediate user wake; sibling active while root settles; central restart after script start; nonzero script exit; running terminal prevents release; old quiesce intent after scheduled wake cannot suspend current work. Drain outbox/await milestones, not sleeps.
- Scheduled tests: bound suspended thread wakes same conversation/PVC; unbound job creates new root once under receipt replay; deleted/edited task race remains covered by existing service; queued prompt does not interrupt running tools.
- Central persistence test: restart using full T3 data directory retains environment ID, settings/auth references, attachments, logs, database and thread execution mappings. Central outage while worker survives preserves approval callback and streams ordered replay on reconnection; worker outage expires the card and uses explicit continuation instead.

The unproven deployment facts are the installed controller version, CSI attachment/reclaim behavior, direct Sandbox NetworkPolicy defaults in the target cluster, and provider-specific durable history layouts under the chosen image. The source supports the direct external-PVC design; tests must establish those deployment facts before claiming complete resume behavior.
