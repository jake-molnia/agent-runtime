# Provider and MCP boundary audit (candidate A)

Source abbreviations: **T3** = `/tmp/t3code-sandbox-research/apps/server/src`; **AR** = `/home/node/.t3/worktrees/agent-runtime/t3-f4b23110`. Every `T3/...` and `AR/...` reference below expands to those absolute roots and gives a source line. This is an implementation design, not a claim that its proposed APIs exist.

## Verdict and usage-first shape

**Put the existing TypeScript adapter runtime beside the agent process in the sandbox, retain T3's orchestration/event store/UI in the single central server, and use the existing Go agent-runtime + Hatchet provisioning path for its allocation binding.** T3 records just the opaque root allocation reference and generation; its existing provider-thread/run/request IDs stay authoritative in SQLite. Existing child delegation inherits that root binding recursively but has a distinct provider session, thread, MCP credential, run and agent identity. The T3 server remains one stable environment ID. The Go runtime can continue supplying generic sandboxd process and file methods, but must not become another T3 conversation orchestrator: the current Go `orchestration/engine.go:1,67,156,235` is expressly coupled to OpenCode; `sandbox/control.go:1,127-153,184-195` is the reusable claim/resolution/pause control; `hatchetbridge/bridge.go:52-100,176` already handles workflow-backed provision and waiting.

Usage: (1) create T3 thread and persist a binding intent keyed to root thread; (2) a Hatchet workflow drives AR's generic claim/readiness and reports `allocationRef, generation, endpoint`; (3) T3 connects to its pinned worker image's versioned TypeScript bridge, opens an *instance-specific* adapter session, and persists/replays normalized events through T3's current event sink; (4) each child is routed to root allocation but creates its own provider/MCP identities; (5) on safe idle release the sandbox, retain native provider data/workspace, and retain T3 history on central PVC; (6) on next turn or scheduled wake, reprovision and resume native session where supported. Expose no sandbox URL or pool selector to the UI. The new bridge is private, allocation-authenticated and fenced by generation.

Small contract (proposed, illustrative; serializable DTOs rather than `Effect`, `Scope`, SDK object handles or callback functions):

```ts
type RootBinding = {
  rootThreadId: ThreadId;
  allocationRef: string;   // opaque Hatchet/agent-runtime ownership handle
  generation: number;      // compare/fence every dispatch and event
  state: "allocating" | "ready" | "quiescing" | "released" | "lost";
};
type WorkerIdentity = {
  rootThreadId: ThreadId;
  appThreadId: ThreadId;
  providerSessionId: ProviderSessionId;
  providerInstanceId: ProviderInstanceId;
  generation: number;
};
interface AgentExecution {
  ensureReady(rootThreadId: ThreadId, operationId: string): Promise<RootBinding>;
  invoke(identity: WorkerIdentity, request: AdapterCommand, operationId: string): Promise<AdapterReply>;
  events(identity: WorkerIdentity, afterSequence: number): AsyncIterable<SequencedAdapterEvent>;
  quiesce(rootThreadId: ThreadId, generation: number): Promise<"idle" | "busy">;
  release(rootThreadId: ThreadId, generation: number, operationId: string): Promise<void>;
}
```

`AdapterCommand` contains the current adapter operations (`openSession`, `ensureThread`, `startTurn`, `steerTurn`, `interruptTurn`, `respondToRuntimeRequest`, `readThreadSnapshot`, `rollbackThread`, `forkThread`, `unloadThread`, optional MCP Apps) based on `T3/orchestration-v2/ProviderAdapter.ts:520-625`. The worker runs these methods locally through the *existing* adapter drivers; the bridge serializes their values/events. The central server still owns access control, model selection, run ordering, durable events and requests. Keep the central `ProviderAdapterV2Shape` as façade if useful, but change its creation at the provider-session boundary, not each driver's SDK internals (`T3/orchestration-v2/ProviderAdapterDriver.ts:26-44`, `T3/orchestration-v2/ProviderSessionManager.ts:78-89,140-170`). `quiesce` must prove zero running turns, pending interactive requests, tools, MCP calls, client terminals and background tasks before termination; idle polling and a single timeout cannot prove it. Binding transitions + operation IDs must be idempotent on the Hatchet side; sequence numbers and generation fence late events, while arbitrary shell side effects remain at-most-reconciled rather than magically exactly-once.

## Why remote low-level process/files are insufficient

There is a genuine process-service seam: Codex constructs an Effect `ChildProcess` and creates the app-server client from the spawned handle (`T3/orchestration-v2/Adapters/CodexAdapterV2.ts:1382-1428,1513-1559`); OpenCode runtime spawns server processes (`T3/provider/opencodeRuntime.ts:602,701`); ACP runtime consumes a child-process spawner and client terminal processes (`T3/orchestration-v2/Adapters/AcpAdapterV2.ts:491-497,1546-1596`). A remote `ChildProcessSpawner` could tunnel standard streams and signals for those paths. It is **not a complete execution boundary**:

- Claude uses `@anthropic-ai/claude-agent-sdk` `query({prompt, options})`, and the SDK itself owns its process/stream (`T3/orchestration-v2/Adapters/ClaudeAdapterV2.ts:28-32,605-635`). Cursor uses `@cursor/sdk` sessions and SDK agent options including cwd/MCP (`T3/orchestration-v2/Adapters/CursorAdapterV2.ts:8-11,305-329,2198-2271`; `T3/orchestration-v2/Adapters/CursorAgentSdk.ts:1-100`). Muse calls `@muse-code/sdk`'s `spawnMspConnection` (`T3/provider/museSdk.ts:4-8,85-101`); these do not use a generic injected Effect spawner. Pi materializes an extension and an interactive JSON process (`T3/orchestration-v2/Adapters/PiAdapterV2.ts:409-445,481-549`). Unless each SDK exposes a remote-process hook, central SDK/adapters still operate in central Node's filesystem, process namespace and lifecycle.
- Direct native filesystem access bypasses injecting `effect/FileSystem`: `T3/provider/Drivers/ClaudeExecutable.ts:2` imports Node FS; `T3/provider/antigravityAuthSupport.ts:2` imports `node:fs/promises`; `T3/provider/EventNdjsonLogger.ts:8` imports Node FS. Adapter attachments and media are read as *local paths* by Codex (`T3/orchestration-v2/Adapters/CodexAdapterV2.ts:3127-3143`), Claude (`.../ClaudeAdapterV2.ts:1364-1380`), Cursor (`.../CursorAdapterV2.ts:2149-2165`), ACP (`.../AcpAdapterV2.ts:6805-6820`), Muse (`.../MuseAdapterV2.ts:1533-1550`), Pi (`.../PiAdapterV2.ts:2334-2350`). The central server's old workspace path is not a remote inode.
- App-server/ACP/Muse/Cursor SDKs have protocol callbacks, streams, OS process lifetime and maps in the adapter, including OpenCode pending requests (`T3/orchestration-v2/Adapters/OpenCodeAdapterV2.ts:1010-1027`), Pi prompts (`.../PiAdapterV2.ts:481-549`) and Muse pending requests (`.../MuseAdapterV2.ts:337,691-721`). A remote spawner cannot move these event loops into a container. Remote filesystem replacement still requires broad coverage across Git, checkpoints, scripts, terminal, preview, attachment and provider config code. Polling a process service for every SDK-generated filesystem operation is not feasible as a transparent intercept.

**Alternative B (central adapter + remote primitives):** feasible only with an intentionally constrained provider slice such as Codex app-server and selected ACP adapters, plus remote `ChildProcessSpawner`, a virtual path/files API, SDK callback bridge, native SDK spawn hooks, central-to-worker command/environment translation and distributed lifecycle fixes. It looks smaller at the first driver but entails invasive per-provider exceptions and leaves third-party SDK-owned processes centrally placed. It also requires central host access to native session files and CLI credentials (or opaque remote FS) and leaves server crashes killing SDK streams. Do not use this as the full built-in-harness architecture. **Alternative C (worker full T3 server/UI per pod):** could keep many adapter internals but violates the fixed one-central-server/no-pairing/no-second-UI boundary and introduces competing SQLite identities. **A**, the worker adapter process with a narrow T3 bridge, retains process/SDK/native session locality and minimizes continuing driver edits; it still requires real distributed fencing and remote workspace feature seams.

## MCP end-to-end, including callback cases

The current central MCP server authenticates bearer credentials (`T3/mcp/McpHttpServer.ts:144-180`). The registry issues 32-byte random thread/provider-session-scoped credentials, hashed in in-memory maps, with liveness TTL, eager revocation and per-thread issuance (`T3/mcp/McpSessionRegistry.ts:52-79,110-217,241-255`); `McpProviderSession` stores active config in a global in-memory thread map (`T3/mcp/McpProviderSession.ts:3-23,44-58`). `ProviderSessionManager` resolves, renews and clears these tokens around thread attach/release (`T3/orchestration-v2/ProviderSessionManager.ts:440-556`). Current endpoint chooses localhost for loopback (`T3/mcp/McpSessionRegistry.ts:90-108`): that becomes *the sandbox itself* from a remote worker. Publish a private internal service DNS endpoint and prohibit a caller from rewriting URL or swapping a token across root/thread/session/generation. Do not put provider account credentials in MCP URL. Reissue scoped tokens on central restart; either worker obtains fresh credentials via authenticated control channel or reconnects its MCP client on resumed session. Central MCP auth registry restart invalidates old tokens even when worker pod survives. Separate app web auth/OAuth and the provider-specific model/health probe path from these MCP credentials.

Direct HTTP path: Claude (`T3/orchestration-v2/Adapters/ClaudeAdapterV2.ts:966-982`), Codex (`.../CodexAdapterV2.ts:1327-1345`), OpenCode 1/2 (`.../OpenCodeAdapterV2.ts:973-991`; `.../OpenCode2AdapterV2.ts:3248-3274`), Cursor (`.../CursorAdapterV2.ts:305-329`), Muse (`.../MuseAdapterV2.ts:1431-1450`) receive central endpoint/header with distinct thread-scoped tokens. ACP's portable path is *stdio MCP to HTTP bridge*: ACP's comment requires stdio and notes uneven optional HTTP/SSE support (`T3/mcp/AcpMcpStdioBridge.ts:12-18`); adapter injects `T3_ACP_MCP_ENDPOINT` and credentials into the bridge (`T3/orchestration-v2/Adapters/AcpAdapterV2.ts:665-730`), and stdio bridge forwards JSON-RPC and SSE to central (`T3/mcp/AcpMcpStdioBridge.ts:119-164,219-269,370-409`); in-process ACP-over-ACP bridge also forwards via HTTP (`T3/mcp/AcpMcpOverAcpBridge.ts:82-133`). Worker image must contain this executable entrypoint, and network policy must allow worker-to-central MCP HTTP. ACP client-terminal fallback also uses that environment and is executed with T3 server privileges in current design (`T3/orchestration-v2/Adapters/AcpAdapterV2.ts:142,1546-1596,1682-1685`), so move terminal implementation/privilege into sandbox.

MCP invocation context on central must verify *actual* thread/provider session and capability, not simply infer root allocation from token (`T3/mcp/McpSessionRegistry.ts:134-162`; `T3/mcp/McpHttpServer.ts:148-180`; `T3/mcp/McpToolAccess.ts:1-110`). Delegated children recursively share worker allocation but issue independent `McpSessionRegistry.issue` scopes. Native subagents that use parent provider session can route through parent MCP scope only if provider's real session identity and access policy say so; test per provider. Codex MCP elicitation server request and MCP Apps are protocol callbacks (above), not generic tool calls, so include them in the bridge matrix. More broadly tool handlers that act on workspace (worktree, project, preview, attachment, device) currently execute central-side (`T3/mcp/toolkits/worktree/handlers.ts:1-90`; `T3/mcp/toolkits/project/handlers.ts:1-90`; `T3/mcp/McpHttpServer.ts:393-451,713-735`): they need allocation-aware file/preview/device operations even if MCP protocol endpoint remains central.

## Restart and safe-idle hazards (blockers)

**P0 — central restart with surviving worker:** startup calls recovery before workers (`T3/serverRuntimeStartup.ts:400-412,507-521`), and shutdown explicitly calls `prepareForShutdown`, then `providerSessions.shutdown`, then `reconcile("shutdown")` (`T3/serverRuntimeStartup.ts:423,449-453`). Recovery today terminalizes nonterminal runs and requests, closes native session state, cancels outbox work (`T3/orchestration-v2/ProviderRuntimeRecoveryService.ts:184-230,444-565,715-765,777-821`); manager explicitly says it *does not resurrect persisted sessions* (`T3/orchestration-v2/ProviderSessionManager.ts:78-89`). Do not simply skip recovery, which strands effects, or keep worker alive without bridge reconnection, which loses SDK callbacks. The minimal **safe initial policy** is coordinated drain: disable new starts, ask worker to quiesce, let bounded work finish or explicitly interrupt/terminalize before central exits; after restart apply existing recovery to unfinished work and resume persisted conversation lazily. If central crashes ungracefully, surviving worker must be fenced/suspended (or terminated) before reconciliation; no silent concurrent continued writes into a run marked cancelled. This preserves conversation but may interrupt active turn. To support *uninterrupted* central rolling restarts later, add durable event cursor, provider-session lease renewal, replayable pending callback IDs, token reissuance and generation/epoch reconciliation before disabling terminalization; this is materially larger and should be proven separately. **Worker restart** is different: native protocol callback handles/processes die, so terminalize in-flight interactive approvals and runs; reprovision from durable workspace/native sessions and resume a later turn. Pod pause similarly loses RAM (`AR/sandbox/control.go:184-195`), thus only after verified safe idle.

**P0 — native state and workspace locality:** sandbox pod termination removes process RAM; only explicitly persistent workspace/provider-home and staged attachments survive. Native references include Pi absolute session-file paths (`T3/orchestration-v2/Adapters/PiAdapterV2.ts:2167-2206`), Codex homes (`T3/provider/Drivers/CodexDriver.ts:148-164`) and ACP binary paths. Stable worker-local mount paths and pinning versions are mandatory. Replacing an allocation must not change absolute repo/native session paths unless the provider supports remapping; no claim that provider `resumeThread` restores an active callback.

**P0 — command/event race:** commit binding/generation centrally before submitting commands; require Hatchet operation ID and generation, reject duplicate `startTurn` and old-generation events, reconcile status on ambiguous ACK, serialize root claim/release and session assignment, retain event cursor until central commits projection. Sequence late native tool events against app run ordinal and provider session identity. Existing scope controls session cleanup (`T3/orchestration-v2/ProviderSessionManager.ts:960-1029,1296-1372`) but does not provide distributed fencing.

**P1 — auth/model/health split:** built-in driver creation does not merely return adapter: Codex creates shadow home, adapter, live snapshot, text generation and usage limits (`T3/provider/Drivers/CodexDriver.ts:148-180,194-203,236-279`); Claude has home + maintenance/cache/snapshot and independent text generation (`T3/provider/Drivers/ClaudeDriver.ts:120-153,168-205,241-261`); OpenCode has 1.x/2.x adapters, server owner and SDK model lookup (`T3/provider/Drivers/OpenCodeDriver.ts:261-321,394-442`). Pi driver builds snapshot, including workspace-sensitive probing (`T3/provider/Drivers/PiDriver.ts:151-196`). Central catalog can retain configured provider *declarations* and control-plane state, but version/executable/installed model, auth health and usage probes often require worker's image, home, and account files. Define a worker read-only probe/snapshot request and a central bounded cache keyed by pinned image + provider instance + credential version; central OAuth callback, account management and secret source remain centrally controlled; inject only the scoped secret needed by this provider into worker. This is a design proposal, **not proof** all providers support safe scoped credential refresh. Avoid parallel refresh-token writers, and never clone central SQLite/home onto workers.

**P1 — full feature routing:** provider bridge alone leaves T3's central direct workspace worktree/Git and filesystem assumptions, checkpoint snapshot/capture, terminals, preview/dev-server ports, user input attachments, MCP filesystem handlers. Make one allocation-aware `WorkspaceExecution` service with operations for stat/read/write/copy/move, constrained git/worktree, checkpoint capture/apply, terminal lifecycle, script process, artifact transfer and preview reverse routing. Keep central authorization and persisted checkpoint metadata. Each operation must be bound to root allocation generation, and project path must be translated to worker-local root. Test actual consumer call paths before claiming full parity. Do not configure old server path as if it were remotely mounted.

## Concrete validation gates

1. Unit: binding inheritance for nested app child vs native subagent, per-session MCP scope, old-generation event rejection, same operation ID retry, concurrent allocate/release/first-turn exclusion; exercise root project path translation and distinct provider/MCP identities.
2. Transport contract: every `ProviderAdapterV2Shape` method and event family serializes; reconnect from sequence cursor without duplicate projection; broker MCP elicitation and ACP terminal callbacks; typed errors and intentional timeout semantics; prove crash before/after command ACK.
3. Provider smoke matrix: pinned image launches/resumes each ten row variants above with worker cwd and home, authenticates/probes catalog, performs one file edit and one MCP tool call, and prompts an approval; test 1.x/2.x OpenCode independently, all ACP allowlisted entries and their stdio bridge, Codex MCP Apps and elicitation, native child activity. Mark any unsupported callback capability before launch.
4. Restart tests: central graceful while idle, central crash with active worker, worker kill during approval (must explicitly fail/cancel pending callback), worker kill after completed turn but before event ACK, lost MCP token on central restart, new allocation preserving native session files, old pod delivering late events. Assert no pending card remains answerable if no live callback and no run is both terminalized and later completed.
5. Feature end-to-end: branch/worktree ops, git diff, checkpoint rollback/fork, attachment media, terminal and scripts, preview URL/browser tools, MCP device screenshot and file export; release compute only once all execution consumers are idle. Keep central T3 DB/PVC single writer and verify UI thread URL/environment ID stable.

### Open assumptions to prove in prototype

The available pinned image can contain licensed/compatible versions of every built-in provider and selected ACP manifests; provider credentials can be scoped/injected without violating SDK auth flows; a workspace/provider-home persistence method retains identical absolute paths; T3's websocket UI is tolerant of allocation wait; AR's existing claim lifecycle accepts a pure generic control call without its OpenCode engine. These are **not source-proven**. The first prototype should host one Codex and one SDK-owned provider (Claude or Cursor) in the worker, connect central MCP via internal DNS, run a typed approval round trip, and kill central vs worker separately. Its successful path must exercise file edit, interruption, session resume and reconnect semantics rather than only printing a model reply.
