# Agent-runtime fit for T3 session sandboxes

Source inspection on 2026-10-08 at agent-runtime commit `476315dba982a73dba526a7c8f9da486c27165db`. This note covers agent-runtime and its installed Kubernetes dependency. It does not establish T3's provider support or prove a running integration.

The existing sandbox package is a good foundation for one sandbox per T3 thread. The existing agent execution engine is specifically an OpenCode runner. Reusing its claim and process/file clients is cleaner than making T3 imitate OpenCode's HTTP API.

## Observed behavior

- Claims already target a named warm pool, use stable keys, enforce ownership on retries, and have a required expiry. `ClaimName` hashes the key; `ClaimWithSpec` validates the pool and spec fingerprint when creation returns AlreadyExists. A T3 thread ID plus allocation generation can supply the stable key. Evidence: [sandbox/control.go](../../sandbox/control.go#L59), lines 59-137.
- Leases include claim UID, sandbox name, host, and expiry. Routing requires the sandbox template to enable its stable service. Attach and delete verify claim identity, and deletion uses foreground propagation. Evidence: [sandbox/control.go](../../sandbox/control.go#L35), lines 35-43 and 139-181.
- Pool resource identifiers exist, but there is no pool inventory/catalog HTTP endpoint in the current binary. Its CLI exposes `serve`, `worker`, and `version`; the worker exposes metrics and starts Hatchet workflows. Pool selection currently comes from trusted agent definition configuration. Evidence: [sandbox/control.go](../../sandbox/control.go#L29), lines 29-32; [command/command.go](../../command/command.go#L19), lines 19-33; [command/worker.go](../../command/worker.go#L24), lines 24-35 and 134-156.
- `Scale(false)` writes `spec.operatingMode=Suspended`. It does not preserve memory and does not wait for observed suspension. This is confirmed by the pinned dependency: Suspended terminates the backing Pod while retaining the Sandbox object and its volumes. The controller actually deletes the Pod. Evidence: [sandbox/control.go](../../sandbox/control.go#L184), lines 184-207; installed `sigs.k8s.io/agent-sandbox@v1.0.3/api/v1beta1/sandbox_types.go:231-235` and `controllers/sandbox_controller.go:1256-1263`. Dependency pin: [go.mod](../../go.mod#L23).
- There are no callers of `Scale` in this repository. Pending OpenCode permissions/forms invoke a wait callback; Hatchet waits for an interaction event or timeout. That releases workflow execution capacity where durable eviction is supported, but the sandbox keeps running. Evidence: [orchestration/engine.go](../../orchestration/engine.go#L328), lines 328-334; [hatchetbridge/wait.go](../../hatchetbridge/wait.go#L26), lines 26-88; repository search `rg 'Scale\\('`.
- The current supervisor stores OpenCode HOME and XDG directories in a newly created temporary directory outside the workspace. A durable `/workspace` alone would not preserve provider session state across Pod replacement. Supervisor ownership and initialized state are also in memory. Tailscale runs with in-memory state and a temporary state directory. Evidence: [runtime/supervisor.go](../../runtime/supervisor.go#L39), lines 39-48, 105-115, 150-153, 206-230; [command/command.go](../../command/command.go#L47), lines 47-58.
- The generic runtime client exposes sandboxd process Start, Execute, WriteStdin, SendSignal, ResizeTTY, and files read/write/list/delete. It connects over gRPC port 9090 and HTTP port 8080. Those can support bootstrap and diagnostics independently of OpenCode. Evidence: [sandbox/runtime.go](../../sandbox/runtime.go#L20), lines 20-44 and 99-151.
- The engine assumes OpenCode end to end: deterministic `ses_`/`msg_` identifiers, Basic authentication, session creation, prompt submission, OpenCode events, permission/form APIs, interrupt, and native session export. It also limits runs to 24 hours and counts user waiting against the execution deadline. Evidence: [orchestration/engine.go](../../orchestration/engine.go#L75), lines 75-99, 187-198, 243-245, 264-278, 305, 365-397, 400-450.
- With an artifact store configured, the successful Hatchet workflow collects the OpenCode session export before deleting the sandbox. Without a store it retains the completed sandbox until expiry. The artifact export is not a generic workspace backup. Evidence: [hatchetbridge/bridge.go](../../hatchetbridge/bridge.go#L55), lines 55-56 and 101-119; [orchestration/engine.go](../../orchestration/engine.go#L437), lines 437-450; [artifacts/store.go](../../artifacts/store.go#L14), lines 14-22.
- The Dockerfile already separates worker and sandbox targets. The sandbox image installs only OpenCode V2, alongside Node, Git, Python, ripgrep, tini, sandboxd, and Tailscale. Its entrypoint starts the OpenCode-specific supervisor. Evidence: [Dockerfile](../../Dockerfile#L12), lines 12-35; [command/command.go](../../command/command.go#L66), lines 66-67.
- Per-claim environment variables and volume claim templates force cold starts. Warm adoption therefore needs a compatible pool template and post-allocation credentials/configuration. Evidence: [sandbox/control.go](../../sandbox/control.go#L64), lines 64-71; installed `sigs.k8s.io/agent-sandbox@v1.0.3/extensions/api/v1beta1/sandboxclaim_types.go:128-138`.

## Recommended integration boundary

These are proposed changes, not existing behavior.

1. Add a T3 allocation service using `sandbox.Control`, with authorized pool discovery and idempotent create, inspect, resume, suspend, and release operations. Keep Kubernetes credentials outside sandboxes and the UI. Return an opaque allocation ID and connection information appropriate to T3's existing remote runtime protocol.
2. Persist a binding between T3 thread ID, allocation generation, claim UID, pool, current runtime endpoint, workspace storage, and desired lifecycle state. Reconcile desired state after control-plane restarts. Treat deletion as its own state that can retry.
3. Build a separate T3 sandbox image and supervisor. Install the exact provider binaries supported by the inspected T3 revision, with pinned versions and a smoke test per provider. Reuse sandboxd and optional network components as useful. Do not route T3 providers through `orchestration.Engine` or the current `Supervisor`.
4. Put worktree data and each provider's resumable session files on storage that survives Pod replacement. Preserve the control-plane conversation separately. Export uncommitted changes, untracked files, and requested artifacts before final release, with explicit retention if export fails.
5. Use distinct lifecycle events for turn completion, waiting for user input, and thread settlement. Do not delete a sandbox merely because an assistant finishes a message. Release on the selected terminal thread event only after durable output capture.
6. Prefer automatic suspension only at validated provider resume boundaries. A provider waiting for an approval may hold an unresolved RPC and process-local state. Pod termination destroys that state. Keep that runtime running until a provider-specific test proves it can reconstruct the pending request, or choose a different infrastructure backend with genuine process checkpoint/restore.
7. A resume must set Running, wait for readiness, bootstrap or reconnect the T3 runtime, rehydrate the provider session, and then deliver the queued user response. Current `Attach` waits for Ready, so it cannot itself wake a suspended sandbox.
8. Apply an inactivity grace period and keepalive policy for terminals, previews, tests, and child tasks before suspension. If those processes must survive unchanged, Kubernetes Pod termination is insufficient.

## Feasibility and evidence still required

Per-thread allocation, pool selection, and cleanup reuse mature mechanisms already present here. A dedicated image is straightforward build work once T3's provider list and Linux installation requirements are known. Durable stop/resume is the hard part: this repository supplies a stop/start operation, not transparent pause.

Before promising automatic pause for every T3 provider, run each provider through an approval request, suspend the Pod, resume on the same storage, and attempt to answer the same request without replaying side effects. Also exercise ordinary between-turn resume, runtime disconnection, user response arriving during suspension, controller restart during claim creation/deletion, export failure, expiry while suspended, and rapid repeated wake requests. No live-cluster or provider recovery tests were performed for this note.
