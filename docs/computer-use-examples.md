# Agent Sandbox example research

Sources fetched on 2026-10-09. Findings describe the published examples and their source code; these deployments were not run locally.

The subsequent implementation is documented in [Sandbox desktop and tools](desktop.md).

The [computer-use overview](https://agent-sandbox.sigs.k8s.io/docs/use-cases/computer-use/) describes capabilities provided by workload images deployed through Agent Sandbox. The Kubernetes controller manages sandbox allocation and lifecycle. The chosen image supplies browser or desktop services. Our pinned `sandboxd` v1.0.3 supplies process and filesystem APIs; it does not itself implement computer actions. [Pinned daemon guide](https://github.com/kubernetes-sigs/agent-sandbox/blob/v1.0.3/packages/sandboxd/USER_GUIDE.md)

## Anthropic Managed Agents

The [Agent Sandbox guide](https://agent-sandbox.sigs.k8s.io/docs/use-cases/anthropic-managed-agents/) describes self-hosting the execution environment for Anthropic Managed Agents. Claude's agent loop and conversation state stay at Anthropic. A worker in the user's cluster executes shell and filesystem operations and returns results. This example does not provision computer-use tools or a browser desktop. The [sample README](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/README.md) identifies this as a preview reference implementation.

The implementation uses the Kubernetes Sandbox resources to allocate workers, rather than adding computer-use methods to `sandboxd`:

1. The dispatcher polls `ant.beta.environments.work.poll`. For each work item, it calls `SandboxClient.create_sandbox` with a template and warm pool, labels the claim with the session ID, reads the allocated pod IP, and POSTs `{session_id, work_id}` to port 8080. [Dispatcher source](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/src/dispatcher/main.py#L96)
2. A warm worker initially runs a small Python HTTP listener. After receiving one session binding, it sets `ANTHROPIC_SESSION_ID` and `ANTHROPIC_WORK_ID` and replaces itself with `ant beta:worker run --workdir /workspace --max-idle 60s --log-format json`. The guide says this CLI acknowledges the work item, downloads skills, executes tool calls, and streams results to Anthropic. The sample delegates the tool implementations to the CLI. [Worker entrypoint](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/src/worker/entrypoint.py#L54)
3. The worker symlinks `/mnt/session/outputs` to `/mnt/gcs/<session_id>`. A GCS FUSE CSI mount persists final artifacts. `/workspace` uses `emptyDir`, so this example's durable output path does not imply a persistent workspace. [Entrypoint storage setup](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/src/worker/entrypoint.py#L66), [sandbox template](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/deploy/base/sandbox-template.yaml)

The [worker image](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/src/worker/Dockerfile) starts from Debian 12 slim and installs bash, Python, Node.js 22, and Anthropic CLI 1.9.1. It installs no Chromium, virtual display, VNC server, screenshot utility, or mouse/keyboard adapter. The sample creates its agent with `agent_toolset_20260401` and verifies a `bash` call using `uname -a && hostname`. There is no `computer` tool registration or MCP service in this example. The sample therefore demonstrates how to connect Anthropic's hosted agent loop to a custom isolated worker image; it is separate from Anthropic's computer-use demo.

The [pod template](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/deploy/base/sandbox-template.yaml) selects gVisor, disables service-account token mounting, runs as a non-root user, makes the root filesystem read-only, and drops Linux capabilities. Dispatcher and worker receive the environment credential. The optional stats adapter uses the organization API key outside the sandbox, reads `work.stats`, and patches warm-pool replicas from `depth + pending` within configured limits. [Autoscaler source](https://github.com/GoogleCloudPlatform/kubernetes-engine-samples/blob/2e79a7b375902c3c761a7c599b9304ade66d74ff/ai-ml/anthropic-agent-sandbox/src/stats-adapter/main.py#L94)

For this repository, the reusable idea is session-bound execution in a purpose-built sandbox image. The Anthropic queue and `ant` worker protocol are specific to Managed Agents. They do not by themselves expose computer-use tools to our other agent harnesses.

## Gemini computer use

The [runtime guide](https://agent-sandbox.sigs.k8s.io/docs/runtime-templates/computer-use/) describes an entire browser agent packaged inside the sandbox. The [Dockerfile](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/gemini-cu-sandbox/Dockerfile) clones Google's `computer-use-preview` repository, installs its dependencies, Playwright, and Chromium, and starts FastAPI on port 8888. The clone is not pinned, so the agent implementation depends on when the image was built.

The [`POST /agent` handler](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/gemini-cu-sandbox/main.py) accepts a natural-language query and optional API key. It sets `PLAYWRIGHT_HEADLESS=1`, takes the Gemini key from the request or environment, and runs `python computer-use-preview/main.py --query ...`. It returns stdout, stderr, and exit code. This endpoint delegates a whole task to another agent; it does not expose individual clicks to an existing harness.

In Google's current [agent implementation](https://github.com/google-gemini/computer-use-preview/blob/77c9797e943aad63bbc963b7fd092a9e51c07863/agent.py), model function calls invoke computer actions, and the resulting URL and PNG screenshot feed the next model turn. The [Playwright implementation](https://github.com/google-gemini/computer-use-preview/blob/77c9797e943aad63bbc963b7fd092a9e51c07863/computers/playwright/playwright.py) launches Chromium and translates actions into page mouse and keyboard operations. Browser state belongs to that agent run.

## AIO sandbox

The Kubernetes [AIO manifest](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/aio-sandbox/aio-sandbox.yaml) selects `ghcr.io/agent-infra/sandbox:1.0.0.152` and port 8080. Its [client example](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/aio-sandbox/main.py) uses the separate `agent-sandbox` Python package to run a shell command, read a file, and stream a browser screenshot. The Kubernetes `agentic-sandbox-client` package manages infrastructure; the AIO SDK controls services inside the container.

The AIO project's current [MCP documentation](https://github.com/agent-infra/sandbox/blob/7f1afaf8d82bd30531a19caeb1a24dfebbc97d8c/website/docs/en/daemon/examples/mcp.mdx) exposes streamable HTTP at `/mcp`. Documented built-in tools include `browser_get_info`, `browser_gui_screenshot`, and `browser_gui_execute_action`. Page-level browser tools come from an additional registered browser MCP server. GUI tools require a running computer-use worker. An advertised tool name alone does not establish that its backing service is available.

The current [computer-use example](https://github.com/agent-infra/sandbox/blob/7f1afaf8d82bd30531a19caeb1a24dfebbc97d8c/website/docs/en/daemon/examples/computer-use.mdx) documents `/v2/computer/actions`, batch actions, screenshots, accessibility nodes, and window queries. Its Computer image provides an XFCE desktop, a `computer-use` worker beside `aiod`, a session D-Bus for accessibility, Chromium support, and noVNC. It demonstrates finding a link by accessible name and invoking it, as well as pixel actions and PyAutoGUI.

These current AIO docs are newer than the image selected by the Kubernetes example. They establish an existing implementation to evaluate, but do not prove that image `1.0.0.152` implements the newer `/v2/computer` APIs or current MCP tool list. Select and pin an image, then verify its reported capabilities and `tools/list` before wiring grants.

## Chrome and Playwright examples

The [Chrome image](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/chrome-sandbox/Dockerfile) installs Chromium and TigerVNC. Its [entrypoint](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/chrome-sandbox/cmd/chrome-sandbox-entrypoint/main.go) starts `Xtigervnc :1`, waits for the display, starts Chromium, and checks the Chrome DevTools Protocol endpoint at `localhost:9222/json/version`. This supplies a browser and display that another controller can drive. It does not supply an LLM agent loop.

The [Playwright image](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/playwright-sandbox/Dockerfile) installs Python Playwright, Chromium, and `@playwright/mcp`. Its [manifest](https://github.com/kubernetes-sigs/agent-sandbox/blob/b6680820545d1b96d2f00cff5bae64ecebfa435d/examples/playwright-sandbox/playwright-sandbox.yaml) runs a Python script that navigates to a URL, prints the title and page text, saves a screenshot, and closes Chromium. It then sleeps to preserve the container for artifact retrieval. The manifest does not start the installed MCP server or connect it to a harness.

## Implications for our runtime

Reuse an existing browser or desktop service and keep the current harness in charge of its agent loop. AIO's computer service is a candidate for full desktop control. Playwright MCP is a smaller candidate when tasks only need a browser. The Gemini pattern fits delegating a complete task to a separate Gemini agent. The Anthropic pattern fits hosting execution workers for Anthropic Managed Agents.

Our [image](../Dockerfile) currently contains no browser or desktop packages. Our [compiler](../definitions/compile.go) already emits selected HTTP MCP connections and exact tool grants. The [URL validator](../definitions/mcp.go) accepts literal loopback HTTP, so a service in the same pod can use a stable local endpoint. Our runtime currently starts OpenCode; other harness integrations still need their own MCP configuration support.

A concrete integration needs a pinned service image, startup and readiness checks, session lifetime management, selected tool grants, and verification that screenshot image content reaches the model. AIO's default port 8080 overlaps with our `sandboxd` REST listener, so a same-pod deployment must configure distinct ports. If using a separate container, share the workspace explicitly when browser downloads and files must be visible to the harness. These are proposed integration steps, not changes implemented by this research.
